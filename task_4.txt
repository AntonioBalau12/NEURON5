## 3. P0 — Fix Factual Confidence Safety

The existing runner uses three confidence tiers.

### Tier 1 — Deterministic Graph Verification

Currently, `exact_fact_match == 1` and `temporal_evidence_match == 1` can raise confidence above 0.90 even when the predicted label is FALSE.

This is unsafe because matching verified evidence generally supports a fact; it does not automatically prove that the entire claim is false.

Required changes:

- Distinguish VERIFIED_SUPPORT from VERIFIED_REFUTATION.
- Respect multi-fact claim semantics.
- Only boost confidence when the evidence supports the actual predicted verdict.
- Never boost FALSE using positive factual support alone.
- Require correct entity, attribute, typed value, date, and provenance.
- Preserve UNKNOWN when evidence is ambiguous.

Use explicit factual verification results rather than inferring factual support solely from two boolean features.

### Tier 2 — FALSE Precision Guardrail

The current policy can convert FALSE predictions into UNSURE when evidence is insufficient.

This may improve precision but destroy FALSE recall.

Evaluate the guardrail quantitatively.

Determine how many:
- Correct FALSE predictions are lost.
- Incorrect FALSE predictions are prevented.
- Claims are converted to UNSURE.

Optimize this trade-off using training-side predictions only.

### Tier 3 — Retrieval-Damped Confidence

Review the current confidence damping and clipping.

Do not arbitrarily increase confidence beyond what is justified by model reliability or independent factual evidence.

Confidence should reflect estimated correctness, not merely the existence of retrieved documents.

## 4. P0 — Proper Probability Calibration

The current `debias_probabilities()` divides predicted probabilities by class weights.

This may approximately reverse class-prior weighting, but it is not guaranteed to produce calibrated probabilities.

Evaluate at least:

- Raw LightGBM probabilities.
- Existing class-weight debiasing.
- Sigmoid/Platt calibration.
- Temperature scaling, if appropriate for multiclass classification.

Use strictly leakage-safe OOF predictions.

Do not fit calibration parameters on the same predictions used for their unbiased evaluation.

Use grouped folds and cross-fitting where necessary.

Evaluate:

- Multiclass log loss.
- Brier score.
- Expected Calibration Error (ECE).
- Reliability by predicted class.
- Confidence payoff under the official competition scoring rules.

Do not assume a calibration method is better without measuring it.

## 7. P1 — Fix Full-Fit Training and Group Leakage

The current production model is trained on all 1,897 examples.

Preserve this capability.

However, the full-fit OOF feature generation uses MD5 hashes of row IDs to create folds.

This may separate near-duplicates or related factual families into different folds.

Replace the ID-hash folds with grouped cross-fitting that respects factual and near-duplicate relationships.

Also inspect whether TF-IDF feature transformations are fitted outside their permitted OOF training partitions.

Avoid contamination in all transformations used for calibration and model-selection evaluation.

The final full-fit production model should be trained using consistent feature definitions and all permitted labeled data.
